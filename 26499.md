# Issue 26499 investigation report

## Scope

Issue: <https://github.com/neovim/neovim/issues/26499>

Problem statement: undo currently replays line-change bookkeeping before extmark undo replay. Since extmark replay is what emits `on_bytes`, undo can call fold evaluation from `changed_lines()` before buffer `on_bytes` callbacks have had a chance to update state. This is visible with expression folds backed by Tree-sitter state.

Checkpoint patch under review:

```text
5bfd2e018c2d90459bc7e3805208204baea7faa7 fix(undo): replay extmarks before line updates
```

Changed files:

```text
src/nvim/undo.c
test/functional/lua/buffer_updates_spec.lua
test/functional/treesitter/fold_spec.lua
```

This report describes what the checkpoint patch does, what it fixes, why it is still half-baked, and what the codebase analysis says about a better fix.

## Original ordering bug

The issue report's minimal ordering problem is:

```text
undo:
  foldexpr
  on_bytes

expected:
  on_bytes
  foldexpr
```

The relevant code paths are:

- `changed_lines()` calls `changed_common()`, and `changed_common()` calls `foldUpdate()` for windows showing the buffer. See `src/nvim/change.c`.
- Extmark undo replay calls `extmark_apply_undo()`. For splice undo, that calls `extmark_splice_impl(..., kExtmarkNoUndo)`, and `extmark_splice_impl()` sends `on_bytes` through `buf_updates_send_splice()`. See `src/nvim/extmark.c`.
- In the old undo flow, `u_undoredo()` applied every `u_entry_T` and called `changed_lines()` before the later loop over `curhead->uh_extmark`.

That order is wrong for clients where fold state depends on `on_bytes`.

## Current checkpoint patch

The checkpoint patch changes `u_undoredo()` so it no longer calls `changed_lines()` immediately inside the `u_entry_T` loop. Instead it records each call's arguments in:

```c
typedef struct {
  linenr_T lnum;
  colnr_T col;
  linenr_T lnume;
  linenr_T xtra;
} u_change_event_T;
```

Then it:

1. Applies all `u_entry_T` text swaps.
2. Replays all extmark undo objects, which sends `on_bytes`.
3. Drains the recorded change vector and calls `changed_lines()`.

This fixes the narrow issue in the simple reproduction: `on_bytes` now runs before fold evaluation during undo.

The patch also adds a focused functional test in `test/functional/lua/buffer_updates_spec.lua` for the issue and updates `test/functional/treesitter/fold_spec.lua` so the previous `#26499` TODO case now expects the fold to stay closed.

Verification run before the checkpoint commit:

```sh

TEST_TIMEOUT=60 \
cmake --build build --target functionaltest

TEST_FILE=test/functional/treesitter/fold_spec.lua \
TEST_TIMEOUT=60 \
cmake --build build --target functionaltest
```

The two full focused test files passed at the checkpoint.

## Why the checkpoint patch is not ready

The patch defers too much.

`changed_lines()` is not just "update folds". It:

- marks redraw ranges;
- calls `changed_common()`;
- updates modified/changelist/window state;
- calls `foldUpdate()`;
- optionally sends buffer line-update events through `buf_updates_send_changes()`.

The line-update event side matters. `buf_updates_send_changes()` collects line data from the buffer at the time the event is sent. If all `changed_lines()` calls are delayed until after every `u_entry_T` has been swapped, then multi-entry undo blocks can send line ranges against the final buffer state, not the intermediate state for the individual entry.

Concrete probe against the checkpoint patch:

```vim
set undolevels=-1
lua vim.api.nvim_buf_set_lines(0, 0, -1, true, {"a", "x", "b", "x", "c"})
set undolevels=1000
lua _G.ev = {}
lua vim.api.nvim_buf_attach(0, false, {
  on_lines = function(_, buf, tick, first, last, new_last, old_bytes)
    table.insert(_G.ev, {
      tick = tick,
      first = first,
      last = last,
      new_last = new_last,
      old_bytes = old_bytes,
      lines = vim.api.nvim_buf_get_lines(buf, first, new_last, true),
    })
  end,
  on_bytes = function() end,
  on_changedtick = function(...) table.insert(_G.ev, { kind = "tick", args = {...} }) end,
})
g/x/d
lua _G.after_delete = vim.deepcopy(_G.ev); _G.ev = {}
undo
lua print(vim.inspect({ after_delete = _G.after_delete, undo = _G.ev, lines = vim.api.nvim_buf_get_lines(0, 0, -1, true) }))
```

Observed undo events from the checkpoint patch:

```lua
undo = {
  {
    first = 2,
    last = 2,
    new_last = 3,
    old_bytes = 0,
    lines = { "b" },
    tick = 6,
  },
  {
    first = 1,
    last = 1,
    new_last = 2,
    old_bytes = 0,
    lines = { "x" },
    tick = 7,
  },
  {
    kind = "tick",
    args = { "changedtick", 1, 8 },
  },
}
```

The final buffer is correct:

```lua
{ "a", "x", "b", "x", "c" }
```

But the first undo line event reports `lines = { "b" }` for an insertion range where a client would expect the line inserted by that specific undo entry. The event is being interpreted after all entries have already been replayed. This can corrupt attached clients that maintain a shadow buffer from `on_lines` or RPC `nvim_buf_lines_event`.

## Open question: can extmark undo records be mapped back to `u_entry_T`?

The useful question from the issue discussion is: why is `ExtmarkUndoObject` not stored in each `u_entry_T`, and can the association be recovered cheaply now?

Current answer: no reliable association exists in the stored data.

Evidence:

- `u_entry_T` stores line undo data only: `ue_top`, `ue_bot`, `ue_lcount`, `ue_array`, `ue_size`, and `ue_next`. It has no extmark range, count, sequence number, or pointer. See `src/nvim/undo_defs.h`.
- `u_header_T` stores two separate header-level structures: `uh_entry` for the linked list of `u_entry_T` records, and `uh_extmark` for all extmark undo objects in that undo header.
- `ExtmarkUndoObject` stores only the object type plus one of `ExtmarkSplice`, `ExtmarkMove`, or `ExtmarkSavePos`. It does not identify a `u_entry_T`.
- Undo file serialization writes all `u_entry_T` records first, then writes all extmark undo objects as a separate stream. There is no per-entry separator, no per-entry extmark count, and no durable boundary information.

The current serialization shape is:

```text
u_header metadata
all u_entry_T records
entry end marker
all extmark undo objects
entry end marker
```

That makes `uh_extmark` a header-level log, not an entry-level log.

## Why count-based or range-based pairing is fragile

The extmark stream does not have a one-object-per-text-change invariant.

Examples from `src/nvim/extmark.c`:

- `extmark_splice_delete()` can push zero, one, or many `kExtmarkSavePos` objects for marks affected by a delete before the corresponding splice object.
- `extmark_splice_impl()` pushes a `kExtmarkSplice`, but it can merge small same-line splices into the previous splice object.
- `extmark_move_region()` stores one `kExtmarkMove`, but the operation sends two splice callbacks: one for removal from the old location and one for insertion at the new location.
- `kExtmarkSavePos` is used for restoring marks and does not itself emit `on_bytes`.
- `ExtmarkSavePos` is not serialized into undofiles, so even any in-memory heuristic involving those records would not round-trip through persistent undo.

Chronological order only helps loosely:

- New `u_entry_T` records are inserted at the front of the header's entry list.
- Extmark undo objects are appended to `uh_extmark` as edits happen.
- Undo iterates `u_entry_T` in entry-list order and iterates `uh_extmark` in reverse order.

For simple multi-line delete cases this order may appear to line up, but there is no boundary marker that says "these extmark objects belong to this `u_entry_T`". Reused single-line undo entries, same-line splice merging, save-position records, moves, and overlapping edits make heuristic pairing unsafe.

## Consequences for a real fix

The checkpoint patch proves that the desired fold/on_bytes order matters, but it also shows that deferring all of `changed_lines()` is too coarse.

There are two plausible directions.

### Option A: store extmark undo records per `u_entry_T`

This is the most direct semantic model:

```c
struct u_entry {
  ...
  extmark_undo_vec_t ue_extmark;
};
```

or equivalently:

```c
struct u_entry {
  ...
  size_t ue_extmark_start;
  size_t ue_extmark_len;
};
```

Then undo could apply one `u_entry_T`, replay only the extmark records associated with that entry, and call `changed_lines()` while the buffer is still in the correct intermediate state.

This is likely the cleanest long-term behavior, but it is not a tiny patch:

- extmark capture currently only asks for the current undo header via `u_force_get_undo_header()`;
- it does not know the active `u_entry_T`;
- undo entry reuse in `u_savecommon()` has to be handled deliberately;
- persistent undo format support needs thought because the current undofile layout stores entries and extmarks separately.

Old undofiles could still be read with header-level extmarks and a compatibility fallback, but new per-entry serialization would need a versioned format change or a backward-compatible optional section.

### Option B: split fold update from the rest of `changed_lines()`

The narrower fix is to preserve per-entry `changed_lines()` event timing while delaying only the fold-sensitive part until after extmark undo replay.

Today the problematic call is in `changed_common()`:

```c
foldUpdate(wp, lnum, last);
```

The comment there says fold updates normally cannot be postponed because a following operator might work on the whole fold. Undo/redo may be a controlled exception because the undo operation already owns the sequence and runs under blocked autocommands while the undo structures are unstable.

A possible shape:

1. During `u_undoredo()`, apply each `u_entry_T`.
2. Call the non-fold parts of `changed_lines()` immediately so `on_lines` and redraw ranges observe the correct intermediate buffer.
3. Replay extmark undo so `on_bytes` callbacks run.
4. Run deferred fold updates for the affected ranges.

This avoids the stale `on_lines` regression without requiring immediate per-entry extmark storage. The risk is that `changed_lines()` currently bundles several side effects together, so splitting it needs careful review of redraw, diff, changelist, and buffer-update behavior.

## Recommendation

Do not proceed with the checkpoint patch as-is.

It is useful as a proof of the ordering requirement and as a test scaffold, but it should be treated as a half-baked baseline. The specific regression risk is stale `on_lines` / `nvim_buf_lines_event` payloads for multi-entry undo blocks.

Recommended next implementation path:

1. Keep the tests that capture the issue behavior.
2. Rework the implementation toward either per-entry extmark undo boundaries or a narrower fold-update deferral.
3. Prefer the narrower fold-update deferral first if the goal is a contained fix for issue 26499.
4. Avoid heuristic pairing between `uh_extmark` and `u_entry_T`; the current data model does not support it robustly.

## Test coverage still needed

The existing checkpoint tests cover the simple ordering bug and the Tree-sitter fold symptom.

Additional tests should cover:

- multi-entry undo with `on_lines` attached;
- RPC `nvim_buf_lines_event` payloads, not only Lua `on_lines`;
- undo after persistent undofile reload, because `ExtmarkSavePos` is not serialized and extmark undo serialization is header-level today;
- `:move` undo, because `kExtmarkMove` sends two splice callbacks but is stored as one extmark undo object;
- same-line edits that trigger extmark splice merging.
